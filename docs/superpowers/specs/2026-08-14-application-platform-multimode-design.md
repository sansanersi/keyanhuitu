# 科研绘图应用平台多模式创作台设计

## 1. 目标与范围

本轮目标是把当前“应用平台”从单一的文生图页，扩展成可实际使用的多模式创作台，并优先完成第一阶段：

1. 文生图
2. 草图转图
3. 编辑图片

本轮重点是把三种模式的前台工作流、参考图上传与保存、生成请求编排和结果展示打通，形成一个真实可操作的应用平台入口。

本轮不做：

- 像素级图片编辑
- 真实 image-to-image 模型推理
- 历史记录页、项目制管理、版本树
- 多图批量生成
- 后端服务拆分或前端框架迁移

## 2. 设计原则

### 2.1 产品原则

- 优先把“可用工作流”做完整，而不是提前做重型后端能力
- 三种模式共享一套主生成链路，避免同一轮内分裂出三套实现
- 上传图片不是临时态，而是应用平台资产，后续可被历史记录与二次生成复用
- 让用户能明确感知当前模式、参考图状态、生成来源和结果边界

### 2.2 工程原则

- 继续复用现有 Flask 单体、`index.html` 单模板和当前 `/api/draw`、`/api/workflow` 主接口
- 模式差异主要收束在 `DrawingApplicationService`，`DrawService` 只做必要扩展
- 第一阶段的数据结构按第二阶段“历史、回填、再编辑”预留，但不提前做过度抽象
- 测试覆盖路由、服务编排、模板产物和现有主链路兼容性

## 3. 用户场景

### 3.1 文生图

用户输入科研绘图需求，配置布局、风格、画布和模型，直接生成图和 workflow。

### 3.2 草图转图

用户上传一张草图或示意图，补充文字说明，例如“按这张草图结构生成更规范的科研机制图”，系统保存参考图，并用“参考图 + 文本需求”共同驱动生成。

### 3.3 编辑图片

用户上传一张现有图片，输入修改要求，例如“保留主体结构，改成更规范的生物示意风格”，系统同样把参考图和文本要求组合成一次新的生成任务。

说明：本轮的“草图转图”和“编辑图片”本质上都属于“参考图驱动的再生成”，不承诺像素级保真编辑。

## 4. 总体方案

推荐采用“共享生成内核 + 模式化应用平台编排”的方案。

### 4.1 方案概述

- 前端新增三模式切换和参考图上传/选择区域
- 应用平台新增“参考图资产”与“生成任务快照”能力
- `/api/draw` 保持主生成入口，扩展 mode 与 reference 相关字段
- `/api/workflow` 可选接入相同上下文，保证三模式下 workflow 也能受参考图语境影响
- `DrawingApplicationService` 负责把模式、参考图和文本统一整理后交给 `DrawService`
- `DrawService` 继续复用当前生成能力，但支持接收参考图语境文本

### 4.2 为什么选这个方案

- 与当前代码结构最贴合，改动集中、风险可控
- 第一轮即可形成“像产品一样能用”的创作台
- 后续第二轮做历史记录、参数回填时，可以直接基于本轮任务快照扩展
- 不会过早引入多套接口和复杂状态机

## 5. 架构设计

### 5.1 前端层

主要改动仍集中在：

- `sci-illust-system/web_app/templates/index.html`

应用平台页将扩展为：

- 模式切换区：`文生图 / 草图转图 / 编辑图片`
- 参考图上传区：仅在后两种模式下展示
- 已保存参考图区：展示当前应用平台已保存的参考图列表
- 当前参考图状态区：明确展示选中的是哪张图
- 结果区：展示本次模式、参考图信息、生成来源、预览图与 workflow

### 5.2 Web 路由层

继续复用：

- `POST /api/draw`
- `POST /api/workflow`

新增应用平台参考图接口：

- `POST /api/app/reference-assets`
- `GET /api/app/reference-assets`

这些接口属于应用平台边界，不混入文本库或图片库的资产维护职责。

### 5.3 应用平台服务层

主要改动文件：

- `sci-illust-system/web_app/services/drawing_app_service.py`

职责调整为：

- 接收 mode、reference_asset_id、reference_summary 等平台级输入
- 读取参考图资产元数据
- 组织标准化生成载荷
- 调用 `DrawService.draw()` 与 `DrawService.workflow()`
- 保存生成任务快照
- 返回前端需要的模式、参考图与结果摘要信息

### 5.4 生成内核层

主要改动文件：

- `sci-illust-system/web_app/services/draw_service.py`

职责保持不变，但新增轻量能力：

- 支持接收 `mode`
- 支持接收 `reference_summary`
- 在进入现有分析与生成流程前，把参考图语境拼入分析上下文

注意：这一层不直接解析图片像素，也不做图像编辑算法，只消费上层提供的参考图说明。

### 5.5 数据访问层

应用平台新增两类核心持久化对象：

1. 参考图资产
2. 生成任务

数据层应继续挂在 `app_db` 边界之内，不回写文本库或图片库逻辑库。

## 6. 数据流设计

一次生成请求的标准流程如下：

### 6.1 前端整理输入

前端根据当前模式整理请求：

- 文生图：文本需求 + 参数
- 草图转图：参考图 + 文本补充 + 参数
- 编辑图片：参考图 + 编辑要求 + 参数

### 6.2 上传或选择参考图

若当前模式为草图转图或编辑图片：

- 用户上传图片到 `POST /api/app/reference-assets`
- 或从已有参考图列表中选择一张资产
- 前端保存 `reference_asset_id`

### 6.3 应用平台编排

应用平台层将请求标准化为统一载荷，例如：

- `mode`
- `text`
- `reference_asset_id`
- `reference_summary`
- `style`
- `layout`
- `canvas_width`
- `canvas_height`
- `model`

其中 `reference_summary` 可以由以下信息拼出：

- 参考图文件名
- 模式类型
- 用户补充描述

必要时可形成类似“参考图为一张用户上传的草图，请在保留结构意图的前提下生成规范科研示意图”的上下文描述。

### 6.4 生成执行

标准化载荷进入：

- `DrawingApplicationService.generate_figure()`
- `DrawingApplicationService.create_workflow()`

再转发给：

- `DrawService.draw()`
- `DrawService.workflow()`

### 6.5 结果回写

生成完成后，将以下内容写入应用平台任务记录：

- 模式
- 用户输入文本
- 参考图资产引用
- 请求参数快照
- 输出 SVG
- 输出摘要
- 输出来源

这一步是第二阶段历史记录与参数回填的基础。

## 7. 存储结构设计

### 7.1 参考图资产表

建议最小字段：

- `id`
- `filename`
- `stored_path`
- `mime_type`
- `size_bytes`
- `mode_scope`
- `created_at`

用途：

- 保存上传参考图
- 为前端提供可回选列表
- 为后续历史记录与再次生成提供稳定引用

### 7.2 生成任务表

建议最小字段：

- `id`
- `mode`
- `prompt_text`
- `reference_asset_id`
- `request_payload_json`
- `result_svg`
- `result_summary`
- `result_source`
- `created_at`

用途：

- 记录一次生成的完整输入输出快照
- 为第二阶段历史记录、参数回填、再次生成打基础

### 7.3 文件存储

参考图文件建议保存到应用平台自己的持久化目录，遵循现有运行时资产根目录习惯，不写回源码目录。

要求：

- 文件名去碰撞
- 保留原始扩展名
- 路径可被前端安全访问或通过 API 间接访问

## 8. 接口设计

### 8.1 上传参考图

`POST /api/app/reference-assets`

请求：

- `multipart/form-data`
- 字段：`file`

返回：

- `success`
- `asset`
  - `id`
  - `filename`
  - `url`
  - `mime_type`
  - `size_bytes`

失败时返回明确错误，例如：

- 未上传文件
- 文件类型不支持
- 文件保存失败

### 8.2 列出参考图

`GET /api/app/reference-assets`

返回：

- `success`
- `items`
  - `id`
  - `filename`
  - `url`
  - `created_at`
  - `mode_scope`

### 8.3 扩展生成接口

`POST /api/draw`

在现有字段基础上增加：

- `mode`
- `reference_asset_id`
- `reference_summary`

保持原接口名不变，兼容当前文生图链路。

### 8.4 扩展 workflow 接口

`POST /api/workflow`

可选接收与 `/api/draw` 相同的 mode/reference 相关字段，使草图转图和编辑图片也能先出结构化 workflow。

## 9. 前端交互设计

### 9.1 模式切换

应用平台左侧新增三模式入口：

- 文生图
- 草图转图
- 编辑图片

切换时要求：

- 明确高亮当前模式
- 切换后更新输入区文案和提示
- 非当前模式的中间状态不污染当前提交载荷

### 9.2 参考图区

在草图转图和编辑图片模式下显示：

- 上传按钮
- 已保存参考图列表
- 当前选中参考图卡片

若未选参考图：

- 禁止直接提交生成
- 给出明确提示

### 9.3 结果区

生成后右侧应展示：

- 当前模式
- 当前参考图文件名（若有）
- 结果来源
- SVG 预览
- workflow 结果
- 摘要信息

### 9.4 文生图兼容

文生图模式保持当前主流程：

- 无需上传参考图
- 继续允许直接生成图片和 workflow

## 10. 风险与控制

### 10.1 风险

- `index.html` 继续承担较多页面结构与脚本逻辑，新增模式后容易让状态分支变乱
- 当前 `DrawService` 是围绕纯文本需求构建的，参考图语境若组织不稳，可能出现行为不一致
- 持久化层当前已有脏工作树和多轮改动，本轮需要避免误伤既有部署链路

### 10.2 控制方式

- 把模式编排尽量收束到 `DrawingApplicationService`
- `DrawService` 只接受已经标准化的轻量参考图上下文
- 参考图存储和任务存储只落到 `app_db` 边界
- 用测试守住现有 `/api/draw` 和 `/api/workflow` 的兼容输入

## 11. 测试与验收

### 11.1 路由测试

至少验证：

- 参考图上传成功
- 参考图列表返回结构稳定
- 空文件、缺失文件、非法文件类型有明确错误

### 11.2 服务测试

至少验证：

- `DrawingApplicationService` 能按 mode 正确组装载荷
- 参考图模式下会把参考图上下文传递给 `DrawService`
- 文生图模式不受新字段影响

### 11.3 现有链路兼容测试

至少验证：

- `/api/draw` 旧输入仍能正常生成
- `/api/workflow` 旧输入仍能正常生成
- 当前弱文本校验逻辑不被破坏

### 11.4 前端产物测试

至少检查：

- 模板内存在三模式切换
- 存在参考图上传区
- 存在参考图列表区
- 存在当前模式和参考图状态展示

### 11.5 部署验收

若本轮进入服务器部署：

- 同步修改后的模板、服务和数据层文件
- 重启 `keyanhuitu` 服务
- 验证 `http://127.0.0.1:5000/` 与 nginx 入口返回 200
- 人工确认三模式切换、参考图上传和生成入口可见

## 12. 第二阶段预留

本轮完成后，可在下一阶段继续扩展：

- 历史记录列表
- 参数回填
- 再次生成
- 已保存参考图复用
- 更真实的图片编辑后端能力

本轮的数据表和任务快照设计必须保证这些能力可渐进接入，而不需要推翻当前结构。
